Deployment Levels From a demo on your laptop to a full DoD production deployment

Every deployment uses the same three pieces: STIG Manager, MySQL, and an OIDC provider. The difference between levels is who provides each piece and what's layered on top.

Level 1 — Beginner

Docker Compose Quick Start

For: Learning, demos, evaluating the tool

Spins up all three pieces in Docker containers with zero configuration. Pre-loaded demo users, no TLS, no real authentication.

docker compose up
  → STIG Manager  (port 54000)
  → Keycloak      (port 8080)  — demo users pre-loaded
  → MySQL         (port 3306)  — empty, ready to go

What You Get

  • Working STIG Manager at http://localhost:54000
  • Login with pre-made demo accounts
  • Full functionality to explore

What You Don't Get

  • No real authentication (demo users only)
  • No encryption (HTTP, not HTTPS)
  • No CAC/PKI support
  • Not suitable for real assessment data

This is the right starting point. Get comfortable with the UI and workflow before worrying about infrastructure.

Level 2 — Beginner

From Source Code

For: Developers, contributors, non-Docker environments

Run the Node.js app directly. You provide MySQL and an OIDC provider yourself.

cd api/source
npm ci
export STIGMAN_DB_HOST=your-mysql-server
export STIGMAN_OIDC_PROVIDER=https://your-keycloak/realms/stigman
node index.js

What Changes from Level 1

  • You install and configure MySQL
  • You install and configure Keycloak (or another OIDC provider)
  • You set environment variables to connect the pieces
  • No Docker involved

Use PM2 as a process manager for anything beyond development.

Level 3 — Beginner

Precompiled Binary

For: Sysadmins who don't want to install Node.js

Download a single executable for your OS (Windows/Linux/macOS) from the GitHub Releases page. No Node.js required.

./stig-manager-linux   # just run it

Same as Level 2 — you still need MySQL and an OIDC provider. Configure via environment variables.

Level 4 — Intermediate

Single Container — Real Deployment

For: Teams with existing infrastructure (MySQL + OIDC already available)

Run just the STIG Manager container. Point it at your organization's existing database and identity provider.

docker run -d \
  -p 54000:54000 \
  -e STIGMAN_DB_HOST=db.yourorg.mil \
  -e STIGMAN_DB_PASSWORD=secret \
  -e STIGMAN_OIDC_PROVIDER=https://keycloak.yourorg.mil/realms/stigman \
  nuwcdivnpt/stig-manager

What Changes

  • Your org already has a MySQL server (maybe AWS RDS)
  • Your org already has an OIDC provider (Keycloak, Okta, Azure Entra)
  • You're adding one container — STIG Manager
  • Can enable native HTTPS with STIGMAN_API_TLS_CERT_FILE and STIGMAN_API_TLS_KEY_FILE

Key insight: STIG Manager is stateless. All data lives in MySQL. The container can be replaced, upgraded, or scaled without data loss.

Level 5 — Advanced

Container + Reverse Proxy (CAC/PKI Auth)

For: DoD environments requiring CAC authentication

Adds an nginx reverse proxy that handles mutual TLS (mTLS) with CAC/client certificates.

┌──────────┐ ┌──────────────┐ ┌───────────┐ │ Browser │────→│ nginx │────→│ STIG Mgr │ │ + CAC │ │ (mTLS/TLS) │ │ API │ └──────────┘ └──────────────┘ └─────┬─────┘ │ ┌─────┴─────┐ │ MySQL │ └───────────┘ │ ┌─────┴─────┐ │ Keycloak │ └───────────┘

How CAC Auth Works

  1. User's browser presents their CAC certificate to nginx
  2. nginx validates the certificate via mTLS
  3. nginx forwards the certificate identity to Keycloak
  4. Keycloak maps the certificate to a user and issues a JWT
  5. STIG Manager receives only the JWT — never touches the certificate

The stigman-orchestration repo provides a complete working example.

nginx Considerations

  • Increase client_max_body_size (default 1MB is too small; use 100M+)
  • Don't buffer streaming endpoints (SSE, WebSocket, NDJSON)
  • STIG Manager sets x-accel-buffering: no which nginx honors automatically
  • WebSocket support requires proxy_set_header Upgrade/Connection
Level 6 — Expert

Kubernetes / OpenShift

For: Large organizations with container orchestration platforms

Same architecture as Level 5, deployed as pods with enterprise infrastructure:

  • Horizontal scaling — multiple STIG Manager replicas (it's stateless)
  • K8s Ingress Controller instead of standalone nginx
  • Managed MySQL (AWS RDS, Azure Database for MySQL)
  • Org-wide OIDC (centralized Keycloak or Azure Entra ID)
  • Iron Bank images — hardened, scanned, DISA-approved
  • Auto-scaling, HA, managed backups

Iron Bank: DoD's hardened container image registry. STIG Manager publishes images there based on Iron Bank's Node.js Alpine images. Use nuwcdivnpt/stig-manager:latest-ironbank or pull directly from registry1.dso.mil.

Level 7 — Expert

Full Production with Automation

For: Mature security programs with continuous monitoring

Everything from Level 6, plus:

  • STIGMan Watcher — monitors filesystem directories, auto-imports .ckl/XCCDF from tools like Evaluate-STIG and SCC
  • C-PAT — POA&M automation connected via the API
  • Custom integrations — scripts/bots using the REST API for metrics, imports, reports
  • Service Jobs enabled — automated database cleanup on schedule
  • Multiple Collections with fine-grained RBAC and ACLs
  • Metrics exports feeding dashboards (Grafana, PowerBI, etc.)

The Full Pipeline

Scanner (SCC/Evaluate-STIG)
  → outputs .ckl/XCCDF files to a watched directory
    → STIGMan Watcher auto-imports into Collection
      → STIG Manager tracks assessments
        → C-PAT generates POA&Ms
          → Metrics API feeds dashboards
