Data Model

Everything in STIG Manager revolves around Collections. Think of a Collection as a bucket that groups related assets together.

STIG Library (system-wide, managed by admins) └── STIGs → Revisions → Rules (with check content + SHA-256) Collection (per-team / per-package) ├── Assets (hosts/servers) │ ├── STIG Assignments (→ references shared STIG Library) │ └── Labels (tags for filtering) ├── Reviews (keyed by Rule Version + Check Content hash) ├── Grants (user/group → role + ACL) └── Metrics (auto-calculated)

See the Data Model & Diagrams page for full interactive Mermaid charts including ER diagram, auth flow, review lifecycle, and more.

How Review Matching Works

This is STIG Manager's killer feature and the thing that makes it fundamentally better than tracking .ckl files.

The Key Insight

Each Review is tracked by a key made from Rule Version + SHA-256 hash of the Check Content. It's NOT tied to a specific STIG revision.

Why This Matters

When DISA releases a new STIG version (quarterly):

ScenarioSTIG ViewerSTIG Manager
Rule unchanged between versions Carries forward (by Rule ID match) Carries forward (by content hash match)
Rule check content changed Still carries forward (wrong!) Flags for re-evaluation (correct!)
Rule ID renumbered but content same Treated as new (loses review) Carries forward (content matches)

Real Example

A STIG rule says "verify the system uses a DoD-approved CA." In the next version, DISA changes it to a specific CA name. STIG Viewer would apply your old "Not a Finding" review to the new rule. STIG Manager won't — the check content changed, so you need to re-verify.

Authentication & Authorization Flow

How Login Works

  1. User opens STIG Manager in browser
  2. Web client redirects to OIDC provider (Keycloak, Okta, etc.)
  3. User authenticates (username/password, CAC, OAuth, etc.)
  4. OIDC provider issues a JWT access token
  5. Browser sends JWT with every API request
  6. API validates the JWT and extracts claims (username, roles, scopes)

Two Layers of Access Control

Layer 1: Application Privileges (from OIDC token)

Set in your OIDC provider (Keycloak roles, Okta groups, etc.). Controls what you can do app-wide.

PrivilegeCapabilities
adminImport STIGs, manage all collections/users, app data
create_collectionCreate new collections (recommended for most users)
userAccess the app (minimum required)

Layer 2: Collection Grants (within STIG Manager)

Set per-collection by Owners/Managers. Controls what you can see and do within a specific collection.

Restricted1None (ACL only)None

Access Control Lists (ACLs)

For fine-grained control, especially with Restricted users. ACL rules combine a Resource (Asset, STIG, Label, or Collection) with an Access level (Read, Read/Write, or None).

ACL Resolution Rules

  1. Direct user grants beat group grants
  2. Highest-priority role wins when user is in multiple groups
  3. Most specific resource wins (Asset+STIG beats Label beats Collection)
  4. On ties, most restrictive access wins

The Stateless Design

Why It Matters

  • The API holds no state — all data is in MySQL
  • You can run multiple replicas behind a load balancer
  • Upgrades are simple: deploy new version, it auto-migrates the database
  • Downgrading requires a database restore from backup
  • Configuration is 100% environment variables — no config files
